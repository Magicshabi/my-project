## 三、固件改造清单

### 3.1 新增三条串口指令

原来固件只有 `CMD_COLOR_GRAB`（46），**一次只能传一个颜色名**（按键路径和串口路径都是 `start(colors, 1)`）。任务二要按口令依次抓 3 个颜色，所以必须新增"序列"入口。

| 功能号 | 名称 | 作用 |
|---|---|---|
| **97** | `CMD_COLOR_GRAB_SEQ` | 一次下发整个颜色序列 + 每个颜色放哪个槽位 |
| **98** | `CMD_COLOR_SET_PLACE` | 设置某个放置槽位的坐标，**立即写 Flash** |
| **99** | `CMD_COLOR_GET_PLACE` | 读回全部 8 个槽位坐标 |

97~102 是原固件 `Global.h` 里未占用的功能号，不会和厂商指令冲突。

### 3.2 放置槽位坐标表（核心改动）

**改之前**：`CG_STATE_PLACE` 把序列里所有颜色都摞在**同一个** `PLACE_X/PLACE_Y` 上，靠 `_stack_count * BLOCK_H` 往上堆高度 —— 这是为"分拣进同一个箱子"设计的。

**改之后**：新增 `_place_tab[8][3]` 坐标表，`CG_STATE_PLACE` 按当前颜色的 `_color_index` 查表：

```cpp
uint8_t ci   = _color_index;
uint8_t slot = getPlaceSlotOf(ci);        // 第 ci 个颜色用哪个槽位
_cur_place_x = _place_tab[slot][0];       // 查表取坐标，不再叠高度
```

**槽位约定**：

| 槽位 | 用途 |
|---|---|
| 0 | 任务一的 **T0** |
| 1 / 2 / 3 | 任务二序列区的 **1 / 2 / 3 号位** |
| 4 ~ 7 | 备用 |

原 `start(colors, count)` 保留下来，变成"所有颜色都放槽位 0"的包装 —— 所以**任务一的行为和原来完全一致**，任务一走老接口即可。

> ⚠️ **未标定前不要跑任务二**。8 个槽位默认值全都是 `(200, -200, 60)`（沿用厂商 demo 的单点），三个位置会重合，会撞在一起。`begin()` 里会打印默认值提醒。

### 3.3 第四色 yellow 补齐

厂商固件里 `red/green/blue` 硬编码在 **4 个地方**（比原先预估的多），现已全部补齐：

1. `kProtoColors[]` / `kOledColor[]` 数组扩到 4 个元素
2. 按键循环的取模 `% 3` → `% KEY_COLOR_COUNT`（=4）
3. `on_key1_select_color()` / `on_key2_start_sorting()` 里的取模
4. `CMD_COLOR_GRAB` 的 `color_id` 映射补上 `4 → "yellow"`

**注意**：这只解决了**主控侧**。K230 视觉模块内部是否认 `yellow` 这个名字，仍然只能实机验证（见第九章）。

### 3.4 ⚠️ 运动流程改动（超出原始需求，需要你确认）

**原逻辑**：松爪后直接横向移动到搜索位。

**问题**：任务二三个放置位各不相同，从 1 号位直接横穿到搜索位**会扫倒刚放好的电池** —— 直接扣"释放后稳定"分，还可能触发"非目标电池被碰倒 -1 分"。

**改法**：`CG_STATE_RESET` 里加了一段"**先原地垂直抬升到 `LIFT_Z`(=220) 再横向移动**"，用 `_cmd_sent` 做一段式门控。

**如果实测发现这段抬升会撞到别的障碍**，回退方法：删掉 `ColorGrabber.cpp` 里 `CG_STATE_RESET` 开头那个 `if (!_cmd_sent) { ... }` 分支，并把 `CG_STATE_RELEASE` 里的 `_cmd_sent = false;` 一并删掉。

### 3.5 掉电保存

槽位坐标通过 `Preferences`（NVS）存到 Flash，掉电不丢：

- 保存：`save_place_slots()`，每次收到指令 98 就自动写一次
- 读取：`load_place_slots()`

> **顺序很关键**：`load_place_slots()` 必须在 `colorGrabber.begin()` **之后**调用。因为 `begin()` 会把 8 个槽位重置成默认值，如果先加载就会被覆盖。当前代码已按正确顺序接在 `register_system_task()` 里。

### 3.6 抓取源坐标表 + 视觉失败兜底（任务一的保底路径）

**为什么需要**：底图把"颜色 → 格位"印死了（见第十一章），所以每个颜色都有**固定**的抓取点。万一 K230 认不出某个颜色（黄色风险最大），机器人不会卡死，而是按坐标去抓。

**新增数据**：`_pick_tab[4][3]` —— 按颜色索引（red=0 green=1 blue=2 yellow=3），外加 `_pick_valid[4]` 记录"是否已示教过"。

> ⚠️ **未示教的颜色不会降级**。这是刻意的设计：没示教过就完全不启用兜底，行为与原始固件一模一样，不会因为没标定就乱抓。

**示教坐标的含义**（这点很重要，容易搞错）：
> 是 **夹爪夹住电池时末端应该在的 XY/Z 位置**（也就是"抓取点"），
> **不是**"相机看到电池居中的位置"。

这样标定最简单：用上位机把夹爪移到正好能夹住电池的姿态，读下 XYZ 就完事。

**三档抓取模式**（指令 102）：

| mode | 行为 |
|---|---|
| 0 | **视觉优先**（默认）：视觉正常就伺服居中抓；连续 8 秒没检测到该颜色 → 降级到坐标 |
| 1 | **强制坐标**：完全不用视觉，直接去示教点抓（K230 坏了也能跑） |
| 2 | **强制视觉**：绝不降级 |

**代码里的分支**：`CG_STATE_DOWN` / `CG_STATE_GRAB` / `CG_STATE_LIFT` 三个状态各加了一条 `if (_coord_mode)` 分支。坐标模式下**直接使用示教点，不再叠加 `X_COMP/Y_COMP` 旋转补偿** —— 因为示教点本身已经是抓取点了，再叠加就成了两倍偏移。

### 3.7 掉落保护（顺带修的一个隐患）

原来松爪后只抬高 40mm 就横移，电池 70×80mm 比 demo 的 30mm 色块大得多，容易扫倒。现已改为**先垂直抬到 `LIFT_Z`(=220) 再横移**。详见 3.4 节。

### 3.8 读实时位姿 + 点动（原固件缺失，标定必需）

**问题**：原固件的 `func_ctrl_callback` 只处理 `id==0xFF` 的少数几条指令，**既没有 `CMD_GET_CUR_COORDS`（读当前坐标），也没有任何机械臂运动指令的转发**。结果是：
- `NexArm.exe` 上位机的"坐标控制"**点了不会动**（能连上、能读版本号，但机械臂不响应、坐标也不刷新）；
- 所以**标定根本无从下手** —— 看不到坐标，也没法把机械臂精确挪到目标点。

**解决**：补两条指令。

| 功能号 | 名称 | 说明 |
|---|---|---|
| **103** | `CMD_COLOR_GET_POSE` | 返回当前末端位姿 6 个 f32（x,y,z,pitch,roll,claw）。内部先 `arm.update_status()` 再泵 150ms 的 AT32 回包，保证数值是新鲜的 |
| **104** | `CMD_COLOR_JOG` | 相对点动。**实现方式是"刷新当前位姿 → 当前位置 + 增量 → 走 `arm.move`（即 `CMD_COORDINATE_SET`）"**，而不是用 AT32 的相对运动指令 `CMD_ARM_MOVE_INC` —— 因为前者已被 ColorGrabber 大量验证可用，风险更低。会夹到 `Robot_Arm` 的坐标限位（x 100~400 / y ±450 / z 20~500） |

配套的交互式标定模式 `calib` 就是套在这两条指令上的，见第八章。

## 四、串口协议速查

### 4.1 帧格式

```
FF FF | id | length | cmd | args... | checksum
```

- `id`：主机下发固定用 `0xFF`
- `length` = **2 + args 字节数**
- `checksum` = `(~(id + length + cmd + args 全部之和)) & 0xFF`
- 多字节整数与浮点**全部小端**

### 4.2 指令 payload 详表

| 功能号 | 方向 | payload |
|---|---|---|
| **97** `CMD_COLOR_GRAB_SEQ` | 主机→主控 | `[count:u8]` + count × `{ [nameLen:u8][name...][placeSlot:u8] }`。`count=0` 表示停止；count 上限 8；name ≤ 15 字符 |
| **98** `CMD_COLOR_SET_PLACE` | 主机→主控 | `[slot:u8][x:f32][y:f32][z:f32]`，共 13 字节 |
| **99** `CMD_COLOR_GET_PLACE` | 主控→主机 | 无参请求；返回 8 槽 × 3 个 f32 = **96 字节** |
| **100** `CMD_COLOR_SET_PICK` | 主机→主控 | `[nameLen:u8][name...][x:f32][y:f32][z:f32]`。name 只接受 red/green/blue/yellow |
| **101** `CMD_COLOR_GET_PICK` | 主控→主机 | 无参请求；返回 4 色 × 3 个 f32 = **48 字节**，顺序固定 red,green,blue,yellow |
| **102** `CMD_COLOR_SET_PICKMODE` | 主机→主控 | `[mode:u8]`，0=视觉优先(超时降级) 1=强制坐标 2=强制视觉 |
| **103** `CMD_COLOR_GET_POSE` | 主控→主机 | 无参请求；返回 6 个 f32 = **24 字节**：x, y, z, pitch, roll, claw |
| **104** `CMD_COLOR_JOG` | 主机→主控 | `[dx][dy][dz][dpitch][droll][dclaw]` 6 个 f32 = 24 字节；相对点动，回返回新的目标位姿（也是 6 个 f32） |
| 45 `CMD_APRILTAG_SET_OFFSET` | 主机→主控 | `[x_off:f32][y_off:f32][z_grab:f32]`，共 12 字节（原有指令，用来调抓取偏移，写 Flash） |
| 46 `CMD_COLOR_GRAB` | 主机→主控 | `[switch:u8][color_id:u8]`，原有指令。color_id：1=red 2=green 3=blue **4=yellow**；switch=0 停止 |

### 4.3 实机帧样例

任务二口令"蓝-红-黄"，依次放 1/2/3 号位：

```
ff ff ff 16 61 03 04 62 6c 75 65 01 03 72 65 64 02 06 79 65 6c 6c 6f 77 03 f4
│     │  │  │  └ count=3 └4"blue"→slot1 └3"red"→slot2 └6"yellow"→slot3
│     │  │  └ cmd=0x61=97
│     │  └ length=0x16=22
│     └ id=0xFF
└ 帧头
```

任务一抓红色放 T0：

```
count=1, {3,"red",0}
```

### 4.4 ⚠️ 一个必须知道的坑

固件把调试日志用 `Serial.printf` 打在**同一个串口**上（`system_task_handle.cpp:436` 的 `serial_port.begin(Serial, 1000000)`）。所以电脑收到的数据流里**日志文本和协议帧是混在一起的**，PC 端解析必须只认 `FF FF` 开头的合法帧、其余当文本丢弃。

`nexarm_cmd.py` 已经处理了这一点（`iter_frames()`），但它意味着**你不能用普通串口助手盲目读**。

### 5.2 命令

```bash
python nexarm_cmd.py --list                            # 列出串口
python nexarm_cmd.py --selftest                        # 不做串口通信，只自检编解码

python nexarm_cmd.py --port COM5 getplace              # 读回全部 8 个槽位坐标
python nexarm_cmd.py --port COM5 place 0 200 -200 60   # 标定槽位 0（T0）
python nexarm_cmd.py --port COM5 place 1 200 -250 60   # 标定槽位 1（序列区 1 号位）
python nexarm_cmd.py --port COM5 offset 20 15 60       # 设抓取偏移（写 Flash）

python nexarm_cmd.py --port COM5 pick red 200 -180 55  # 示教红色电池的抓取点
python nexarm_cmd.py --port COM5 getpick               # 读回 4 个颜色的抓取点
python nexarm_cmd.py --port COM5 pickmode 0            # 0=视觉优先 1=强制坐标 2=强制视觉

# ★ 标定主力：交互式标定（点动 + 一键把当前位置存进表里）
python nexarm_cmd.py --port COM5 calib

# 单次读位姿 / 点动
python nexarm_cmd.py --port COM5 pose                  # 读当前 XYZ
python nexarm_cmd.py --port COM5 pose --watch          # 连续刷新
python nexarm_cmd.py --port COM5 jog 5 0 0             # X 方向 +5mm

python nexarm_cmd.py --port COM5 seq red:0                       # 任务一
python nexarm_cmd.py --port COM5 seq blue:1 red:2 yellow:3       # 任务二（暂缓）
python nexarm_cmd.py --port COM5 stop                            # 停止
```

### 5.3 已通过的自检项

- 帧编解码往返一致
- 小端 f32 往返正常（`200.0 → 00 00 48 43`）
- `getplace` 96 字节能正确解码
- **日志噪声过滤**：把帧夹在 `[CGRAB] ...` 日志中间仍能正确解出
- `offset` 帧 `length=14`，满足固件 `length >= 14` 的判定
- `pick` payload 19 字节（含颜色名），帧 `length=21`，满足固件 `alen >= 14` 的判定
- `getpick` 48 字节能正确解码并还原颜色名

### 5.4 已知现象

**打开串口会让主控复位一次**（DTR/RTS 电平变化），这是 ESP32 的正常行为。脚本里已加 1.5 秒等待和缓冲区清理，但你要知道面板会重启一次。

## 八、标定执行手册 —— 任务一（当前主线）

> **目标**：把 4 块电池中指定的那一块抓起来，准确放进 T0。
> **标定本质**：把机械臂末端移到正确位置，把**那一刻的 X/Y/Z 直接存进表里**。

### ⚠️ 先说一件重要的事：别指望上位机

原 AI 视觉固件的 `func_ctrl_callback` **只处理 `id==0xFF` 的少数几条指令，既没有"读当前坐标"，也没有任何机械臂运动指令的转发**。

所以 `NexArm.exe` 上位机的"坐标控制"在这套固件下**点了不会动**（能连上、能读版本号，但机械臂不响应、坐标也不刷新）。

为此我在固件里补了两条指令（103 读位姿 / 104 点动），并把它包装成一个**交互式标定模式**：

```bash
python nexarm_cmd.py --port COM5 calib
```

进去之后这样用：

```
calib> p            查看当前位姿
calib> x 5          沿 X 点动 +5mm   （还有 y / z / t(pitch) / r(roll) / c(claw)）
calib> place 0      把【当前 XYZ】一键存成槽位 0（= T0）
calib> pick red     把【当前 XYZ】一键存成红色电池的抓取点
calib> grip / open  夹爪闭合 / 张开
calib> list         打印两张表
calib> h            帮助        q 退出
```

> **关键优势**：坐标是"读当前位姿 → 直接写进 Flash"，**完全不用手抄数字**，也就不会抄错。

任务一要用到**两张表**：

| 表 | 含义 | 要标几个 | calib 里的命令 |
|---|---|---|---|
| 放置槽位表 | **放到哪里** | 1 个（槽位 0 = T0） | `place 0` |
| 抓取源坐标表 | **从哪里抓** | 4 个（每个颜色一个） | `pick <颜色>` |

### 第 1 步：烧录并确认通信（前提）
- 按第七章烧录，确认串口日志里出现 `1.0.1-match`；
- `python nexarm_cmd.py --port COM5 pose` 能打印出当前位姿，就说明通了。

### 第 2 步：固定机械臂与底图（⚠️ 最关键）
- 机械臂底座固定在工作台上，**标定期间绝对不能再挪动**；
- 底图按规则铺好、位置固定。
- **这一步没做好，后面所有坐标全部作废。**

### 第 3 步：怎么标 T0（放置点）

```bash
python nexarm_cmd.py --port COM5 calib
```

```
calib> p          ← 先看现在在哪
calib> x -20      ← 逐步点动，把末端挪到 T0 中心正上方
calib> y 15
calib> z -30      ← 下降到合适高度
calib> open       ← 张开夹爪
calib> p          ← 目视确认位置对了
calib> place 0    ← 一键存成槽位 0 = T0  ✅
```

> **Z 取多少**：默认 60 是厂商为 **30mm 高**色块调的。**你的电池 70×80mm，明显更大**，高度必须自己试。
> **建议**：第一遍先示教得**高一点**（比如松开后电池从 5mm 高度落下），保证不压不撞；跑通之后再逐步降低优化。

### 第 4 步：标定 4 个颜色的抓取点
底图上 4 个格位是**印死的**（布局见第十章）：

| 颜色 | 底图格位 | 相对位置 |
|---|---|---|
| 红 red | 电池A | 左上 |
| 黄 yellow | 电池B | 右上 |
| 蓝 blue | 电池C | 左下 |
| 绿 green | 电池D | 右下 |

仍留在 calib 里，对每个颜色重复：

```
calib> x 60       ← 点动到目标格位上方
calib> z -40
calib> open
calib> p          ← 确认夹爪对准格位中心、且夹爪开口能容下电池
calib> pick red   ← 一键存成红色的抓取点  ✅
```

四色依次做完 `pick red` / `pick yellow` / `pick blue` / `pick green`，最后 `list` 确认。

> **⚠️ `pick` 的 Z 就是抓取高度**（夹爪夹住电池时的高度），**直接使用，不再叠加任何补偿**。它和 `offset`（视觉专用补偿）是两套东西，别混淆。
> **省时间技巧**：4 个格位均匀 2×2 排布，先标一个，其余三个按格位间距点动过去、微调后存——比重新找位置快得多。

### 第 5 步：先用「强制坐标」把整条运动链路跑通
在碰视觉之前，先用坐标模式确认机械部分是对的：
```
python nexarm_cmd.py --port COM5 pickmode 1     # 强制坐标，完全不依赖 K230
python nexarm_cmd.py --port COM5 seq red:0
```
应该看到：直接去红色格位 → 下降 → 夹 → 抬到 LIFT_Z → 移到 T0 → 放 → 垂直抬起 → 结束。

**这一步跑通价值很大**：它把"运动学 / 坐标 / 夹爪"整条链路一次性验证干净，后面视觉出问题也不会怀疑到这里。

跑偏了怎么调：

| 现象 | 调哪里 |
|---|---|
| 抓的位置偏了 | `pick` 的 x / y |
| 放的位置偏了 | `place 0` 的 x / y |
| 抓不住 / 压太深 / 夹空 | `pick` 的 z |

### 第 6 步：切回视觉模式，验证 K230
```
python nexarm_cmd.py --port COM5 pickmode 0     # 视觉优先，超时自动降级
python nexarm_cmd.py --port COM5 seq red:0
```
看串口日志：
- `-> SEARCH` 后正常居中锁定 → **视觉通了**；
- 出现 `vision timeout -> COORD grab` → **视觉没认出红色，已自动降级**。流程照样跑完，但说明 K230 那边要查。
- 想确认视觉到底行不行，把 pickmode 设成 `2`（强制视觉）——认不出就会一直停在 SEARCH 不动。

### 第 7 步：⭐ 验证 K230 认不认 `yellow`
```
python nexarm_cmd.py --port COM5 pickmode 2     # 强制视觉，认不出就会卡住
python nexarm_cmd.py --port COM5 seq yellow:0
```
- 机械臂朝黄色电池动 → **认 `yellow`**；
- 一直停在 SEARCH 不动 → **不认**，走第九章待办 1 的退路。

> 也可以不用电脑：KEY1 循环到 OLED 显示 `YELLOW`，按 KEY2 启动。

### 第 8 步：标 `offset`（可选，只影响视觉模式）
`offset`（x_off / y_off / z_grab）是**视觉模式专用**补偿：视觉居中之后还要往哪边挪一点才真夹得住。坐标模式不用它。
```
python nexarm_cmd.py --port COM5 offset <x_off> <y_off> <z_grab>
```

## 十、底图布局实测（2026-09-13 通过照片确认）

底图是一张约 **540mm** 宽的图纸，关键区域如下：

```
┌──────────────────── 图纸约 540mm ────────────────────┐
│ 电池摆放区(250x300mm)                 图纸尺寸540…    │

│ │ 电池A 红 │ 电池B 黄 │   │  T0 基础摆放区         │ │
│ ├──────────┼──────────┤   │  (100x200mm)           │ │
│ │ 电池C 蓝 │ 电池D 绿 │   │  空框，任何颜色都能放  │ │
│ └──────────┴──────────┘   └────────────────────────┘ │
│ （单块电池尺寸7x8cm）        10cm / 15cm 标尺          │
│                                                       │
│        序列摆放区 + 精度评分框（同心圆）  ← 已暂缓     │
└───────────────────────────────────────────────────────┘
```

### 关键确认：**颜色 → 格位是底图印死的**

| 底图格位 | 颜色 | 相对位置 |
|---|---|---|
| 电池A | 红 red | 左上 |
| 电池B | 黄 yellow | 右上 |
| 电池C | 蓝 blue | 左下 |
| 电池D | 绿 green | 右下 |

> **这条结论非常重要**：它意味着"哪个颜色在哪里"是**静态、可预知**的，所以"按坐标抓"完全成立 —— 这就是 3.6 节那张抓取源坐标表的基础。

### 实测尺寸汇总

| 项目 | 数值 | 来源 |
|---|---|---|
| 图纸尺寸 | 约 540mm | 图上印刷 |
| 电池摆放区 | 250 × 300mm | 图上印刷 |
| T0 基础摆放区 | 100 × 200mm | 图上印刷 |
| 单块电池 | 70 × 80mm（7×8cm） | 图上印刷 |
| 电池外接圆直径 | √(70²+80²) ≈ **106mm** | 推算 |

### 由尺寸推出的两个结论

1. **任务一的"放入 T0"很宽松**：T0 是 100×200mm，电池 70×80mm，就算朝向最不利也至少有 **±10mm** 余量。这 15 分相对好拿。
2. **任务二的"完整落入内框"才是硬骨头**：内框是同心圆，而电池外接圆就有 106mm，所以内框直径必须 > 106mm 才可能完整落入，可用偏差 =(内框直径−106)/2。**（该部分已暂缓）**
