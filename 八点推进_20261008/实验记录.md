# S3 分叉实验（2026-10-08 20:5x）：改用 GUI 同款原始写帧

S2 现场判定：**没动**。按 S3 换 GUI 同款"原始舵机写帧"：
`CMD=3(写寄存器)`, `ARGS=[41(ACC), acc=100, pos(int16LE), 0, 0, speed=2000]`（8 字节），
并**同时对比 ID 寻址方式**（GUI 用 `send_packet(servo_id,…)`，但固件里存在 `id != 0xFF → return` 早退分支，必须实测）。

脚本：`八点推进_20261008/id6_raw_write_probe.py`　原始日志：`logs/s3_raw_write_*.log`

## 结果（读数为辅助，**不作为判据**）

| 阶段 | 寻址 | 命令 1751 → 读数 | 命令 1841 → 读数 | 结论 |
|---|---|---|---|---|
| **A** | **ID=6（舵机号）** | 1755 | 1837 | ✅ **设备接受**，账面跟随 |
| **B** | **ID=0xFF（广播）** | 1798 | 1798 | ❌ **被忽略**（4 次读数纹丝不动） |

### ✅ 本轮确证（协议级，可直接写入规格）

1. **原始舵机写帧必须用「舵机号」寻址**（`ID=6`）；`ID=0xFF` + `CMD=3` **无效**。
   → 解决了我此前对 GUI 究竟发哪个 ID 的疑问：**GUI 用的是舵机号**（Codex line 29 的描述正确）。
2. 帧字节：`ffff 06 0a 03 29 64 <pos_lo> <pos_hi> 00 00 d0 07 <xor>`
   （LEN=10=2+8；acc=100/speed=2000 为 GUI 默认；校验 = `~sum(ID..ARGS)&0xFF`）。

### ⚠️ 仍未解决（需要现场触觉/目视）

读数跟随**仍不能证明舵机实际转动**（D1）。当前存在两个互斥解释：

- **解释①（账面 echo）**：AT32 只更新内部目标，舵机没动 → 力矩未开 / 舵机未响应。
- **解释②（真实回读）**：AT32 读的是舵机 `PRESENT_POSITION`，A 阶段舵机**真的转了 42 ticks（3.7°）**，
  但用户看不到夹爪动 → **ID6 舵机与夹爪机构可能脱开/打滑**。

**判定方法（下一次执行）**：请人**用手直接拨动夹爪**，随后读取 ID6 位置：
- 读数**跟着手变** → 解释②（真实回读）→ 问题在机械联动，不在协议；
- 读数**仍停在 1798** → 解释①（账面 echo）→ 问题在力矩/舵机响应；
- **掰不动** → 力矩是开着的（这本身就否掉了「KEY1 未解锁」的旧假设）。

# S4 大行程判定（2026-10-08 20:59）：幅度拉到 44°

## 前置新事实（来自现场触觉）

用户反馈：**夹爪「根本掰不动（很硬）」** → **力矩是开着的**（舵机在锁位）。

→ 这条**推翻了 10-07 的「KEY1 未解锁 / 力矩关着」推断**（该推断原本就只是读源码得来，
  而设备当日 19:11 已刷回出厂程序）。勘误 E3 由此**从「待判定」升级为「已否证」**。

## 实验

## 判据（现场目视，决定性）

**44° 的张开/闭合是肉眼看不可能错过的幅度。** 两种结果两种结论：

- **看到了明显开合** → 写路径成立；此前"没动"纯粹是 ±4° 幅度太小 + 观测条件不足 → 直通八点。
- **仍然完全不动** → 结合「力矩已开」，则 **AT32 的账面是"目标 echo"，命令并未落到舵机** ——

  （让用户在 `NexArm.exe` 里拨一次夹爪滑块，从它的十六进制日志区导出），与我的帧逐字节比对。
