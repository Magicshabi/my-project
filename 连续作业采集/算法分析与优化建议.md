# 算法设计草案分析与优化建议

基于 `算法设计草案.md` 的详细分析，记录关键问题和实施建议。

## 总体评价

**✅ 优点**：
- 架构清晰：索引→编译→队列→状态机，层次分明
- 安全意识强：版本绑定、原子状态切换、不临时补边、request_id防重发
- 明确边界：承认无视觉/传感器限制，不伪造能力
- 验证优先：先离线测试，再实机验收，循序渐进

**⚠️ 需要解决的问题**：
1. 过渡段数据缺失（最关键）
2. Dijkstra图搜索过度设计
3. 完成判据不明确
4. 占位管理未细化
5. 故障恢复算法缺失

## 问题1：过渡段数据缺失（最关键）

### 现状

当前数据结构：
- `scene.json`：场地版本
- `初始位采集/home.json`：P0（1个点）
- 12条 `route.json`：每条8个点（S1～S8）

**缺失的连接段**：
- P0 → 首篮S1（12种组合：红/黄/蓝/绿 × P1/P2/P3）
- 上一条S8 → 下一条S1（需要的组合数未定）
- 末篮S8 → P0（如果需要自动回位）

### 问题

- 连接段的数据格式是什么？也是8个点？还是直接关节直线？
- 存储在哪？`连接段采集/` 文件夹？
- 验证标准是什么？避障？用时？
- 如果连接段未验证，执行器能启动吗？

### 第一版建议：硬编码简化连接

```python
# 连接段暂时用关节直线，保守速度
def build_transition(from_point, to_point):
    return {
        'type': 'joint_line',
        'from': from_point,
        'to': to_point,
        'speed': 300,  # 保守速度
        'acceleration': 50,
        'verified': False,  # 标注未验证
    }
```

**验收时人工确认**：
- 执行器慢速运行整个连接段
- 肉眼观察无碰撞
- 记录实际用时
- 标注 `verified: True`

### 第二版：专门采集连接段

数据结构建议：
```json
{
  "from": "P0",
  "to": {"color": "红", "target": "P1", "point": "S1"},
  "waypoints": [...],  // 可选中间点，空表示直线
  "verified": true,
  "max_speed": 500,
  "clearance_notes": "越过支架顶部20mm"
}
```

存储位置：`连接段采集/P0_to_红P1.json`

## 问题2：Dijkstra图搜索过度设计

### 实际情况

三篮连续搬运的路线是**固定的**：
```
P0 → 篮1_S1~S8 → 篮2_S1~S8 → 篮3_S1~S8
```

不存在"多条可选路径"，因为场地是固定的。唯一的变化是颜色组合（4³=64种），但每种组合的路线序列是确定的。

### 第一版建议：硬编码连接逻辑

```python
def build_action_queue(colors: list[str]) -> list[Action]:
    """为三篮搬运生成动作队列。"""
    actions = []
    
    # 1. P0 → 首篮S1
    actions.append(Transition(from='P0', to=(colors[0], 'P1', 'S1')))
    
    # 2. 首篮完整路线
    for i in range(1, 9):
        actions.append(PickPlace(color=colors[0], target='P1', stage=f'S{i}'))
    
    # 3. 篮1_S8 → 篮2_S1
    actions.append(Transition(from=(colors[0], 'P1', 'S8'), 
                               to=(colors[1], 'P2', 'S1')))
    
    # 4. 第二篮
    for i in range(1, 9):
        actions.append(PickPlace(color=colors[1], target='P2', stage=f'S{i}'))
    
    # ... 依此类推
    
    return actions
```

**不用图搜索**，等未来扩展到回收、补篮、多区域时再引入。

- 没有定义"接触判据"：是看反馈差值？还是电流？还是固定延时？

**必要停留时间多少？**
- 文档说"保留必要停留"，但没给具体值

### 建议：明确每个阶段的完成条件

## 问题4：占位管理未细化

### 问题

- 预计占位如何更新？每个动作完成后？
- 如果掉篮，系统不知道，占位记录就错了
- 下一批开始时，用户说"已复位"，软件如何核对？只能信任用户？

### 建议：证据级别标注

```python
class OccupancyLevel(Enum):
    USER_CONFIRMED = 'user_confirmed'  # 用户明确提供
    PREDICTED = 'predicted'  # 软件推测，可能错
    SENSOR_VERIFIED = 'sensor_verified'  # 有传感器确认（当前不可用）


class OccupancyState:
    """占位状态，明确证据级别。"""
    source_baskets = {
        '红': OccupancyLevel.USER_CONFIRMED,  # 用户说已复位
        '黄': OccupancyLevel.USER_CONFIRMED,
        '蓝': OccupancyLevel.USER_CONFIRMED,
        '绿': OccupancyLevel.USER_CONFIRMED,
    }
    target_areas = {
        'P1': OccupancyLevel.PREDICTED_EMPTY,  # 预计为空
        'P2': OccupancyLevel.PREDICTED_EMPTY,
        'P3': OccupancyLevel.PREDICTED_EMPTY,
    }
    gripper = OccupancyLevel.PREDICTED_EMPTY
```

**验收时人工核对**篮子位置，记录失败case。

## 问题5：故障恢复算法缺失

### 问题

文档说"核对后生成恢复计划"，但没说具体怎么恢复：
- 如果在S5掉篮，恢复计划是什么？回到S4重试？还是放弃本篮？
- 如果在S8松爪后发现篮子翻了，怎么办？
- 如果通信中断恢复后，如何确定当前状态？

### 第一版建议：不自动恢复

遇到故障就HOLD，等用户介入：

```python
def on_fault(fault_type, context):
    """故障处理：冻结队列，等待人工介入。"""
    freeze_queue()
    log_state(context['batch_id'], context['action_index'], context['last_feedback'])
    
    # 保持姿态但不僵硬
    release_torque_but_keep_position()
    
    # 通知用户
    notify_user(f'故障：{fault_type}，请检查现场')
    
    # 用户介入后，可选：
    # 1. 手动复位到P0，发新指令
    # 2. 如果只是通信中断，调用resume()
```

**第二版再加自动重试逻辑。**

## 实施优化建议

### 短期（第一版可用）

1. **简化连接段**：
   - P0→首篮S1、篮间连接用关节直线 + 保守速度
   - 不做图搜索，硬编码三段固定连接
   - 验收时人工确认不碰撞，记录实际用时

2. **明确完成判据**：
   - 写死每个阶段的容差、稳定时间、停留时间
   - S4/S5/S6只检查ID1-5，不检查ID6
   - 先用保守值，实测后调优

3. **占位采用"信任但验证"**：
   - 每批开始读取真实姿态，匹配允许起点（P0或上次S8）
   - 占位状态标注证据级别（用户确认 vs 预测）
   - 验收时人工核对篮子位置，记录失败case

4. **故障处理暂时人工介入**：
   - 遇到超时/越界/通信中断立即HOLD
   - 记录完整状态到日志
   - 用户介入后决定：回P0重来 or 手动恢复+resume

### 中期（验收后优化）

5. **补完连接段数据**：
   - 单独采集P0→12个首点、需要的篮间连接
   - 定义连接段数据格式和验证标准
   - 存储到 `连接段采集/` 文件夹

6. **实测耗时并调优**：
   - 记录每个阶段的实际耗时：发送→到位→停留
   - 找出瓶颈（通信？运动？停留？）
   - 调整速度、停留时间、采样频率

7. **引入图搜索（如果需要）**：
   - 如果扩展到回收、补篮、多起点，再引入Dijkstra
   - 当前固定场景用不上

### 长期（扩展功能）

8. **自动恢复**：
   - 通信中断恢复：读取姿态，匹配未完成动作，续执行
   - 掉篮重试：回到本篮S1，重新执行S1~S8（需要先验证）

9. **轨迹混合**：
   - 当前设计是"点到点衔接"，每个示教点会减速
   - 真正不停速需要轨迹混合，但这是另一个大topic
