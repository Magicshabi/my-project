# 连续搬运算法草案

状态：核心交互规则已于2026-10-12由用户确认；本文是算法设计，不是已实现或通过实机验收的连续执行器。实际采集进度以progress_tracker及主文件为准。

## 已确认规则

- 输入“红-蓝-黄”形式的三种不同颜色，依次对应目标区域P1/P2/P3。
- 第一版按固定场地的示教点查表，不接视觉动态定位。
- 完成后停在最后一条路线的S8，不自动回P0。
- 用户手动将篮子放回源位、清空三个目标区域，再发新指令；空闲状态收到新指令即表示本批场地准备完成，不再追加准备确认。
- 执行期间的新搬运指令立即返回BUSY，不排队、不替换当前任务，也不把被拒指令记成下一批就绪。
- 以上仅针对正常空闲启动；故障后仍先核对状态、诊断和恢复，不能用新指令直接清除故障。

## 目标

收到指令后快速找到已采集路线，预先组成动作队列；每个动作达到完成条件后立即进入下一阶段。减少运行中的文件读取、规划等待和人工继续。提速不等于直接增加舵机速度，也不取消夹爪必要停留。

## 一、启动时建立索引

读取并校验scene、P0、12条route以及独立过渡段，建立内存索引：

```text
route_index[(场地版本, 颜色, 目标区域)] -> Route(S1…S8, 文件SHA, 验收状态)
transition_index[(起始节点, 结束节点)] -> 经过验证的连接段列表
```

每条连接段还带允许的源篮/目标占位、夹持状态、场地绑定、时间估计和验证证据。路线数据校验通过与运动可用分别管理。发现文件或配置版本变化则让缓存失效，不能继续用旧计划。

固定点位方案下，“定位”是从索引取出示教关节目标，不是视觉定位，也不是直接由XYZ猜舵机刻度。

## 二、把用户指令编译为队列

先校验输入恰好包含三种不同的合法颜色，再按顺序绑定P1/P2/P3，例如：

```text
[(红, P1), (蓝, P2), (黄, P3)]
```

检查颜色、任务ID去重，以及所有路线/连接段是否可用。正常空闲时，用户本次输入提供“源篮已复位、目标区已清空”的现场依据；软件将其标为用户提供的状态，不冒充传感器观测。再读取实际机械臂姿态并匹配允许起点。先生成整批计划，再发第一条运动指令。一次批次的示意：

```text
初始连接 -> 红到P1(S1…S8) -> 已验证连接
         -> 蓝到P2(S1…S8) -> 已验证连接
         -> 黄到P3(S1…S8) -> 停留等待下一条指令
```

PREPARE、EXECUTE及恢复过程中收到新搬运指令立即拒绝并提示BUSY；不排队。输入检查及IDLE到PREPARE的切换必须原子完成，防止同时收到两条指令导致双重执行。

每次受理生成batch_id，动作使用(batch_id, action_index)。接口应附带request_id防止网络重发执行两次；同一request_id返回原任务结果，用户主动重复同样的颜色序列则使用新的request_id。不能仅按文本相同去重。

## 三、连接段选择

将已验证的等待位、过渡点和路线端点构成小图；边是已验证的动作段。首先按当前占位、夹爪状态与场地版本过滤不可用边，再按预计耗时用Dijkstra选择连接路径。

每条边的代价可用同步运动预计时间加必要停留时间；图中没有边表示缺少运动验证，不能用关节直线临时补边。占位会随搬运变化，因此不能只按颜色缓存一条永久通路。

初始姿态通过实测反馈与允许起点比对；找不到匹配起点时进入独立回位规划，不能单纯取“最近点”然后直接跳转。

第一批通常从P0连接到首篮S1。后续批次从上一批最后S8连接到新首篮S1，采用用户已复位后的占位状态；这类跨批连接要单独验证，不能照搬批内连接的占位前提。用户手动复位篮子可能碰动机械臂，因此每批仍读取实测起点，不盲信上次保存的S8。

## 四、执行状态机

```text
IDLE -> PREPARE -> EXECUTE_STAGE -> NEXT_STAGE -> … -> BATCH_DONE -> IDLE
                         |
                         +-> HOLD/FAULT
```

运行状态至少包含batch_id、action_index、route_id、stage、负载状态、最后反馈及目标。每个动作使用唯一编号，重复回执或重发指令不能让索引推进两次。

正常完成条件按动作类型区分：

- MOVE：运动轴到位且满足阶段所需稳定条件；搬运期间ID6维持夹紧目标，不拿被把手挡住的实际读数去要求达到闭合目标。
- GRIP_CLOSE：只写ID6，判断已完成合爪动作或达到经验证的接触判据，并保留必要停留；仅凭电机停住不能宣称已经抓到篮子。
- GRIP_OPEN：臂体维持落地姿态，只张爪，达到张开条件后撤离。
- TRANSITION：检查该连接的起点、占位与负载前提，再按MOVE执行。

完成后action_index加1，直接取得内存中的下一动作。不扫目录、不重新读取全部JSON、不再次请求“继续”。如果只做到“轨迹队列自动衔接”，仍可能在示教点减速；真正的速度连续要另做轨迹混合验证。

每阶段的目标、运动轴、到位容差、稳定条件、超时和夹爪停留预先存入动作对象，来自对应路线已验证的参数，不在执行中临时放宽。反馈必须属于本次动作发送后的采样，重复或过期回包不能提前推动队列。

以下是队列控制伪代码，不包含任何可直接驱动设备的命令：

```text
on_command(text, request_id):
    if request_id已处理: 返回该任务状态
    原子检查并占用IDLE；若忙碌: 返回BUSY
    解析三种不同颜色；绑定P1/P2/P3
    场地状态 := 用户本次提交确认已复位
    获取设备锁；读取并核对真实姿态和配置
    编译并校验整批路线、过渡段和文件版本
    若无法生成可执行计划: 释放锁，报告具体缺项；不发送运动
    action_index := 0
    启动当前动作

on_fresh_feedback(feedback):
    若故障条件成立: 冻结队列，进入FAULT，记录恢复所需状态
    否则若当前动作完成且未推进过:
        更新阶段及预计篮子位置
        action_index += 1
        若还有动作: 启动下一动作
        否则: 保持最后S8，关闭串口并释放锁，进入IDLE
```

查找路线使用字典，单条平均O(1)；执行中取下一动作也是O(1)。连接图搜索只在整批准备时进行。真正影响节拍的主要是机械运动、串口反馈和必要停留，必须用阶段实测耗时定位瓶颈，不能把查表速度当作机械臂运动速度。

## 五、反馈、占位和故障

动作完成是控制器结论；篮子抓取/放置成功是物理结论。没有视觉或夹持传感器时只能维护预计占位，明确标注证据级别，不能伪造自动识别掉篮的能力。每批开始的场地准备和现场干预按用户约定处理。

单串口、单执行队列持有设备锁。轨迹参数预计算，反馈判定和日志记录避免互相阻塞。通信缺失、超时、越界或版本变化时冻结后续队列；能通信时保持姿态并保留夹持目标，不自动松爪。

恢复时读取真实姿态、夹持/场地状态及未完成动作，核对后生成恢复计划。进程重启不直接执行磁盘里的action_index，也不自动重试不明确是否完成的动作。

## 实现与验证顺序

1. 先实现离线指令解析、路线索引、连接选择和队列编译；错误颜色、重复颜色、缺路线/连接、占位冲突和版本不匹配全部拒绝。
2. 用模拟反馈测试阶段只推进一次、过期反馈不推进、忙碌指令拒绝、同request_id不重复执行、正常结束返回IDLE。
3. 97点和连接数据具备且验证合格后，再接实际串口；按单路线、连接段、完整组合顺序验收。
4. 记录各阶段规划耗时、发送耗时、到位耗时和停留耗时，再决定具体提速项。第一版不凭空指定三篮完成秒数。

核心算法已可据此实现。输入接口可以后续选择命令行、上位机或消息接口；统一调用同一个on_command，不改变队列与阶段算法。暂停/急停硬件语义和自动掉篮检测仍需独立设计与验证，不影响先完成离线规划器。
